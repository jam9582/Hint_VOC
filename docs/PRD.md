# VOC 통합 관리 (8D) — 개발 명세 (Claude Code용 단일 기준 문서)

> 이 문서가 개발의 유일한 기준이다. 원본은 PRD_VOC v2(docx)이고, 로그인·권한·기술 스택은 팀 논의로 추가했다.
> `[확인 필요]`로 표시된 곳은 추측해서 만들지 말고 먼저 질문한다.

## 0. 작업 규칙 (Claude Code는 반드시 지킬 것)

1. 이 문서를 끝까지 읽고, 12장의 단계 계획을 **한 번에 한 단계만** 진행한다. 순서는 내가 정하면 바꿀 수 있다. (15장 결정 10)
2. 각 단계가 끝나면 (a) 무엇을 만들었는지, (b) 13장 완료 조건을 어떻게 직접 확인하는지, (c) 다음 단계를 알려 주고 **멈춘다.** 내가 "다음"이라고 하면 넘어간다.
3. **7장 데이터 구조(표 이름, 열 이름, 타입, NOT NULL)는 임의로 바꾸지 않는다.** 바꿀 필요가 생기면 멈추고 이유와 함께 질문한다. (DB는 다른 팀원이 만든다.)
4. DB 접근 코드는 한 곳(예: `lib/db/`)에 모아, 나중에 표 이름이나 열 이름이 바뀌어도 고칠 곳이 적게 한다.
5. 비밀 키(`service_role` 등)는 브라우저 코드에 절대 넣지 않는다. 키는 `.env.local`에 두고 `.env.example`만 커밋한다.
6. 예시 데이터는 모두 가상이다. 실명, 실제 회사 데이터, 유료 도구는 쓰지 않는다.
7. 디자인 다듬기는 나중이다. 지금은 단순하고 읽기 쉬운 화면이면 된다. 휴대폰 화면(폭이 좁을 때)에서도 깨지지 않게 한다.

## 1. 제품 개요

- **앱 제목**: VOC 통합 관리 (8D)
- **한 줄 설명**: 품질·생산기술 실무자가 소음, 기능 고장, 전장, 누수, 외관 등 모든 유형의 VOC를 8D 단계 단일 양식으로 한곳에 기록하고, 차대번호·부품 LOT로 생산·부품 이력과 과거 유사 VOC를 자동 연결해 보며, 필수 항목이 비면 다음 단계로 넘어가지 못하게 하고, 지연 건은 알림으로 받아 효과 검증이 끝나야 종결되도록 하는 웹 앱.
- **대상 사용자**: 품질·생산기술 실무자 (VOC 접수부터 종결까지 담당)
- **해결할 문제**: VOC마다 엑셀·수기 문서가 따로 있고 양식이 달라 이력·진행 단계를 찾기 어렵다. 차대번호 같은 필수 정보나 처리 단계가 빠져도 알아채기 어렵다. 그 결과 자료 재탐색과 고객 재문의로 원인 확인이 늦어지고, 빠진 단계 때문에 같은 불량이 재발한다.

## 5. 기능

### Must
| # | 기능 | 설명 |
|---|---|---|
| 1 | VOC 등록 (D0~D2) | 웹 입력 폼 하나로 모든 유형을 등록한다. 유형을 고르면 그 유형의 추가 항목(8장)이 폼에 나타난다. 저장하면 VOC 번호가 자동으로 붙고 단계는 D3이 된다 |
| 2 | 단계 잠금 | 각 단계의 필수 항목(6장 표)과 유형별 필수 추가 항목이 비면 "다음 단계" 버튼이 눌리지 않고, 비어 있는 항목 이름을 알려 준다 |
| 3 | 이력 자동 연결 | 차대번호를 입력하면 차량 정보(차종, 생산일, 공장, 라인, 근무조)를 붙여 보여 준다. 부품 번호를 입력하면 그 차량에 장착된 부품의 LOT와 협력사를 붙여 보여 준다. 없으면 "이력 없음"을 표시한다 |
| 4 | 유사 VOC 표시 | 등록 화면과 상세 화면에서 아래 중 하나에 해당하는 과거 VOC를 최근 순으로 보여 준다. ① 같은 부품 번호이면서 같은 부품 LOT ② 같은 유형, 같은 부위, 같은 부품 번호 ③ 같은 차종, 같은 유형, 같은 부위 |
| 5 | 현황 목록 | 모든 VOC를 단계별로 보고, 단계·등급·유형·부위·차종·담당으로 거른다. 기한이 지난 VOC는 빨간색 |
| 6 | 종결 조건 | D6 검증 결과가 "합격"이고 D7 표준 반영 문서가 적혀 있어야 종결할 수 있다. 불합격을 저장하면 단계가 D4로 돌아간다 |
| 7 | 단계 이력 | 단계가 바뀔 때마다 언제, 누가, 어느 단계에서 어느 단계로 옮겼는지 남긴다 |
| 8 | 로그인·권한 (팀 추가) | 3장 기준 |

### Should (Must가 끝난 뒤)
| 기능 | 설명 |
|---|---|
| 지연 알림 | 매일 한 번, 단계 기한을 넘긴 VOC 목록을 담당자에게 메일로 보낸다. 같은 VOC는 하루에 한 번만(`alerted_on`). 안전·법규 등급은 접수 즉시 알린다 |
| 같은 문제 묶음 경고 | 유사 VOC 조건 ① 또는 ②에 해당하는 미종결 VOC가 2건 이상이면 현황 맨 위에 경고 |
| 효과 지표 요약 | 현황 위에 필수 정보 누락률, 평균 원인 확인 일수, 평균 종결 일수, 재발률, 기한 초과 건수 표시 |

### 이번에는 안 함
MES·ERP 실제 연동, 통계 대시보드, AI 유사 VOC 검색, 협력사 SCAR 회신 화면, 고객 진행 상황 자동 알림, 사진·녹음·영상 직접 첨부(링크 칸으로 대신), FMEA·작업표준서 개정 연동, 부서별 세부 권한(일반/관리자 2가지만).

## 6. 업무 규칙

### 6-1. 단계 흐름
```
접수(D0~D2, 폼 저장) → D3 → D4 → D5-D6 → D6검증 → D7-D8 → 종결
```
- 저장하면 `stage = D3`.
- 효과 검증(`d6_result`)이 "불합격"이면 `stage = D4`로 돌아간다. 되돌린 사실을 `voc_stage_log`에 남기고 `note`에 이유를 적는다. 되돌린 뒤의 기한과 입력 내용은 15장 결정 7, 8을 따른다.
- 등급이 "안전·법규"이면 D3 기한이 짧아지고(당일) 접수 즉시 담당자에게 알린다(알림은 Should).

### 6-2. 단계별 필수 항목과 기한 (기한은 예시 값, `[확인 필요]` 회사 기준)

| 단계 | 필수 항목 | 기한 |
|---|---|---|
| D0~D2 접수 | 접수 경로, 등급, 담당, 차대번호, 주행거리, 유형, 부위 대분류, 부품명, 증상 설명, 발생 빈도, 재현 여부, 유형별 필수 추가 항목 | 접수 당일 |
| D3 임시 봉쇄 | 봉쇄 범위(LOT·기간·차종), 봉쇄 조치 | 접수 후 2일 (안전·법규는 당일) |
| D4 근본 원인 | 발생 원인, 유출 원인, 재현 검증 결과(재현됨) | 접수 후 7일 |
| D5~D6 대책 | 발생 대책, 유출 대책, 적용 시작 차대번호 또는 LOT, 검증 기준 | 접수 후 14일 |
| D6 효과 검증 | 검증 결과(합격/불합격), 검증 근거 | 검증 기준에서 정한 기간 |
| D7~D8 종결 | 표준 반영 문서, 수평 전개 대상(없으면 "없음"), 고객 확인 결과 | 검증 후 7일 |

- `voc.due_at`은 현재 단계의 기한이며, 단계가 바뀔 때마다 위 규칙으로 자동 계산한다.
- **[확인 필요]** D6 효과 검증 기한: 원본에 숫자가 없다. 확정 전까지 "D6 시작일 + 14일"로 가정한다.
- **[확인 필요]** D4 필수 "재현 검증 결과(재현됨)": `d4_verified`가 "재현됨"이어야 다음 단계로 가는지, 값만 채우면 되는지 확인한다. 확정 전까지는 "값이 채워져 있으면 통과"로 한다.

### 6-3. 종결 조건
`d6_result = 합격` 이고 `d7_docs`가 비어 있지 않아야 종결 가능. (D7~D8 단계 필수 항목도 모두 채워야 한다.)

### 6-4. VOC 번호
`VOC-연도-일련번호` (예: `VOC-2026-0001`). 연도별로 4자리 일련번호. 동시에 두 명이 등록해도 중복되면 안 되므로 **DB 쪽에서 만든다** (함수 또는 시퀀스 + 기본값). 사이트 코드에서 번호를 직접 만들지 않는다.

### 6-5. 유효성 검사 위치
| 규칙 | 어디서 |
|---|---|
| 7장의 필수(NOT NULL), 차대번호 17자, 주행거리 0 이상 | DB 제약 + 사이트 폼 둘 다 |
| 단계별 필수 항목(D3~D8) | 사이트 서버 코드 (DB는 NULL 허용) |
| 유형별 필수 추가 항목(8장) | 사이트 서버 코드 |
| 종결 조건 | 사이트 서버 코드 |

## 7. 데이터 구조 (PostgreSQL 기준)

**타입 대응**: 문자열(n) → `varchar(n)` / 긴 글 → `text` (2,000자 이내) / 정수 → `integer` / 날짜 → `date` / 날짜시간 → `timestamptz` (표시는 Asia/Seoul) / 코드 → `varchar`, `code` 표에 있는 값만 허용 / 예·아니오 → `boolean` / JSON → `jsonb` / 링크 목록 → `text` (쉼표로 구분한 주소)

**표 구성** (PRD 6개 + 계정용 1개)

| 표 | 한 줄의 뜻 | 연결 |
|---|---|---|
| voc | VOC 한 건의 접수 정보 | vin ↔ vehicle (아래 참고) |
| voc_8d | VOC 한 건의 8D 진행 내용 | voc_id → voc (1:1) |
| voc_stage_log | 단계가 한 번 바뀐 기록 | voc_id → voc (1:N) |
| vehicle | 차량 한 대의 생산 이력 | vin |
| vehicle_part | 차량 한 대에 장착된 부품 하나 | vin → vehicle |
| code | 선택 항목에 쓰는 코드 하나 | 각 표의 코드 열 |
| profiles (팀 추가) | 로그인 계정의 이름·유형 | id → auth.users |

> **[확인 필요]** 팀에서는 표가 8개라고 했다. 위는 7개다. 나머지 1개가 무엇인지 정해지면 이 장에 추가한다.

### 7-1. voc

| 열 | 항목 | 타입 | NOT NULL | 입력 방법 |
|---|---|---|---|---|
| voc_id | VOC 번호 | varchar(20) | **PK** | 자동 (VOC-연도-일련번호) |
| received_at | 접수 일시 | timestamptz | O | 직접 입력, 기본값 지금 |
| channel | 접수 경로 | 코드 | O | 고객센터 / 딜러 / 정비소 / 온라인 / 사내 |
| grade | 등급 | 코드 | O | 안전·법규 / 기능 / 감성 |
| owner | 담당 | varchar(30) | O | 직접 입력 (이름 또는 역할) |
| vin | 차대번호 | varchar(17) | O | 직접 입력, 17자가 아니면 막음 |

### 7-8. 표 사이 연결 주의 (DB 담당과 확인)

- **voc.vin → vehicle.vin 외래키는 걸지 않는 것을 권장한다.** Must 3에서 "vehicle에 없는 차대번호는 '이력 없음'으로 보여 준다"고 했으므로, 외래키를 걸면 이력이 없는 차량의 VOC는 저장 자체가 막힌다. 조회할 때만 join한다.
- voc의 부품 정보와 vehicle_part의 연결은 `voc.vin = vehicle_part.vin AND voc.part_no = vehicle_part.part_no`.
- 코드 열(channel, grade, voc_type 등)이 code 표의 값만 갖게 하는 방법(트리거 또는 사이트 검사)은 DB 담당과 정한다.
- 권한 정책(RLS): 로그인한 사람은 읽기만 한다. 쓰기는 사이트 서버 코드만 하고, 삭제와 code·계정 수정은 서버 코드가 `role = admin`인지 확인한다. 3장 기준. (15장 결정 11)

## 10. 테스트 데이터 요청 (DB 담당 팀원께, 가상 데이터)

완료 조건(13장)을 확인하려면 아래 경우가 데이터에 들어 있어야 한다.

1. code 표: 9장 전체
2. vehicle 5~10대 (차대번호 17자, 차종 2~3종, 공장·라인·근무조 섞기)
3. vehicle_part: 차량당 부품 2~3개. 서로 다른 차량이 **같은 part_no + 같은 part_lot**를 갖는 경우 포함 (유사 VOC 조건 ①)
4. voc 10건 이상: 유형 골고루(NVH, FUNC, ELEC, LEAK, APPR 포함), 단계 골고루(D3~종결)
5. 같은 part_no + 같은 LOT의 VOC 2건 이상 (유사 VOC, 같은 문제 묶음 경고)
6. 기한(`due_at`)이 어제인 미종결 VOC 1건 이상 (빨간색 확인)
7. vehicle에 **없는** 차대번호로 접수된 VOC 1건 (이력 없음 확인)
8. 종결된 VOC 2건 이상, 그중 1건은 종결 후 90일 안에 같은 부품 번호·같은 유형으로 다시 접수된 건 (재발률)
9. D6 불합격으로 D4에 되돌아간 VOC 1건과 그 voc_stage_log
10. 계정: 일반 계정 1개, 관리자 계정 1개
11. 실명, 실제 회사 데이터 금지. 예시: 수납함 소음, 파워윈도 작동 불량, 도어 누수, 도장 들뜸

| Step 10 Should | 같은 문제 묶음 경고 → 효과 지표 요약 → 지연 알림(메일) 순서 | 13장 Should 확인 |
| Step 11 마무리 | 13장 전체 체크리스트 점검, README(실행 방법), 남은 `[확인 필요]` 목록 정리 | 모든 완료 조건 통과 |

각 단계 끝에서 반드시 멈추고 보고한다 (0장 규칙 2). 순서는 내가 정하면 바꿀 수 있다 (15장 결정 10).

## 13. 완료 조건 (기능 하나에 한 줄)

| 기능 | 완료 조건 |
|---|---|
| Must 1. VOC 등록 | 유형을 "누수·누유"로 고르면 유체 종류와 발생 상황 칸이 나타난다. 필수 항목을 모두 채워 저장하면 voc에 voc_id가 붙고 stage가 D3인 새 줄이, voc_8d에 같은 voc_id의 빈 줄이 생긴다 |
| Must 2. 단계 잠금 | 차대번호를 비운 채 저장하면 줄이 추가되지 않고 "차대번호"가 빠졌다고 표시된다. 유형이 NVH인데 소리 성격을 비워도 마찬가지다. D4에서 유출 원인을 비우면 다음 단계 버튼이 눌리지 않는다 |
| Must 3. 이력 자동 연결 | vehicle에 있는 차대번호를 입력하면 차종·생산일·라인이 보이고, vehicle_part에 있는 부품 번호를 입력하면 부품 LOT과 협력사가 보인다. 없는 값이면 "이력 없음"이 보인다 |
| Must 4. 유사 VOC 표시 | 같은 부품 번호·같은 LOT의 VOC가 이미 1건 있을 때 새 VOC를 입력하면, 그 VOC 번호가 유사 VOC로 보인다. 유형이 다른 VOC는 조건 ①에 맞을 때만 보인다 |
| Must 5. 현황 목록 | 유형을 "전장·전자"로 거르면 그 유형의 VOC만 보인다. 기한이 어제인 미종결 VOC는 빨간색으로 보인다 |
| Must 6. 종결 조건 | D6 결과를 "불합격"으로 저장하면 stage가 D4로 돌아간다. "합격"이어도 d7_docs가 비면 종결 버튼이 눌리지 않는다 |
| Must 7. 단계 이력 | VOC 한 건을 D3에서 D4로 넘기면 voc_stage_log에 from_stage D3, to_stage D4인 줄이 하나 생긴다. 불합격으로 되돌리면 되돌린 기록도 남는다 |
| Must 8. 로그인·권한 | 로그인하지 않고 주소로 들어가면 로그인 화면으로 간다. 일반 계정에는 삭제·code 관리·계정 관리가 보이지 않고, 관리자 계정에는 보인다 |
| Should. 지연 알림 | 기한이 지난 VOC가 있을 때 매일 확인을 실행하면 담당자에게 목록 메일이 한 통 간다. 같은 날 다시 실행해도 더 가지 않는다 |

## 14. 남은 확인 사항 (모아 보기)

**팀이 답해야 하는 것** (임의로 정할 수 없다)
1. 표 8개 중 나머지 1개가 무엇인지 (7장)
2. 적용 전 지표 값(원인 확인 일수, 종결 일수, 재발률, 기한 초과 건수): 팀이 센 숫자가 있는지

3. 3장의 vehicle, vehicle_part 수정 화면이 필요한지: 3장 권한표에는 있지만 4장 화면과 12장 Step 9에는 없어 만들지 않았다. 지금은 조회만 된다
4. 재발률 기준 (15장 결정 16): 종결된 VOC를 기준으로 계산했다. 팀 기준이 다르면 바꾼다
5. 지운 VOC 번호의 재사용: 마지막 번호를 지우면 다음 등록이 그 번호를 쓴다. 재사용을 막아야 하는지
6. 배포 위치와 지연 알림 예약 실행: 호출 주소만 있고 매일 자동 실행은 연결되지 않았다
7. 메일 서버: 실제 메일 서비스로 보내는 시험은 하지 않았다

**임시 기준으로 진행하고, 팀이 확정하면 바꾸는 것**
8. D4 "재현됨"이 통과 조건인지 (6-2): 값이 채워져 있으면 통과
9. D6 효과 검증 기한 숫자 (6-2): D6검증 시작일 + 14일
10. vehicle_part의 PK (7-5): `(vin, part_no)`
11. voc.vin → vehicle 외래키 (7-8): 걸지 않음
12. 3장 권한표: 3장 표대로
